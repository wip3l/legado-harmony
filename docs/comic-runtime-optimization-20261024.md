# 漫画 AI 着色：2026-10-24 真机优化记录

本轮在用户设备上完成旧版与优化版交替测试。稳态 Worker 单页耗时中位数：竖图降低 6.8%，横图降低 8.3%，512 方图降低 8.9%，256 小图降低 35.4%。这些是同一素材的重复测量，不代表所有漫画、设备或长时间运行的收益。

## 环境与方法

- 设备：HOP-AL10，系统 `7.0.0.109(SP6C00E105R4P4)`，API 26；NNRT 返回 `NPU_ohos.boot.hardware.Kirin9030Pro_v2_0`。
- 主应用：4.4.931 调试构建。AI 子库基线：`bdfcfd14ed7b4088a647efa372d29347278c7984`；优化版是该提交之上的本轮工作区改动。
- 基线在独立临时源码目录构建，保留与优化版相同的应用版本和测试入口；没有切换或回退用户工作区。
- 使用设备中已有的专用测试图（1350×1920），生成旋转横图、512×512 方图、256×256 小图。测试不读取用户书籍。
- 前台启动真实应用，测试期间保持窗口亮屏，结束后恢复窗口原属性。按旧版、优化版、旧版、优化版顺序运行，每轮 25 次，共 100 次实际着色。
- 每种尺寸每轮运行 6 次，剔除第 1 次，合并同版本两轮的 10 个样本取中位数。每轮最后另做一次从小图返回方图，检查动态模型尺寸恢复。
- 竖图、横图实际选用 NNRT；方图、小图强制 CPU，便于独立比较 CPU 路径。每轮使用新的 Worker 和本轮内存中的后端校验记录。

计时从向生产 Worker 投递任务到收到 JPEG 结果，包含解码、输入准备、推理、合成、JPEG 编码和消息往返；不含下载、模型资源提取、主应用队列等待、结果落盘及界面显示。所有基准计算均绕过结果缓存命中。

前期探索运行出现后台/亮屏状态差异，CPU 曾测得 7～8 秒甚至更长。这些结果不纳入下表，不能据此宣称数倍提速。

## 对照结果

| 场景 | 后端 | 旧版中位数 | 优化版中位数 | 耗时降低 |
| --- | --- | ---: | ---: | ---: |
| 1350×1920 竖图 | NNRT | 1575 ms | 1467.5 ms | 6.8% |
| 1920×1350 横图 | NNRT | 1634.5 ms | 1499.5 ms | 8.3% |
| 512×512 方图 | CPU | 2912.5 ms | 2654.5 ms | 8.9% |
| 256×256 小图 | CPU | 1061.5 ms | 685.5 ms | 35.4% |

首张 NNRT 仍需加载和质量校验：旧版每轮首张约 7.8～8.4 秒，优化版约 7.7～8.4 秒，未见稳定的首次校验提速。表中收益主要适用于后续页面。测试未修改网络结构、权重、输入尺寸策略、JPEG 95、CPU 4 线程、`preferred_fp16` 或 NNRT 性能模式。

## 实现

1. 固定 NPU 画布的补白和裁剪移到 `libcomic_pixels.so` 按行处理，保留 ArkTS 回退。尺寸已经匹配时省去复制；输入子视图仍复制成紧凑缓冲区，保证模型拿到正确的底层数据。
2. 常规 CPU 推理复用动态模型，尺寸变化时重新检查并调整输入。驻留缓存只保留一个模型：已有 NPU 模型时，穿插一张 CPU 图不驱逐它；连续两次普通 CPU 请求才切换为 CPU 缓存。
3. 首次 NNRT 校验的 FP16/FP32 参考独立加载，不参与上述 CPU 缓存，不改变已有质量与速度选择门槛。

额外混合序列验证了“竖图×2 → 小图 → 竖图 → 方图×2 → 竖图”。穿插小图前后竖图分别为 1471 ms 和 1475 ms，日志确认返回 NPU 时 `reused=true load=0ms`；连续 CPU 后回到 NPU 为 3309 ms，需要重新加载模型。两次返回竖图的 JPEG 也与基线逐字节一致。该序列用于检查缓存切换行为，不计入性能表。

## 验证与证据

- 四轮共保存 20 张 JPEG，每种场景的文件 SHA-256 在四轮间完全相同，包括从小图切回方图的结果。
- 真机原生合成对照：6 组、301324 个通道，最大误差 0/255。
- 真机原生补白/裁剪对照：9376035 个 Float32 值，最大误差 0，包含横竖画布、数组偏移和非法缓冲区检查。
- 最终版本 `offlineInferenceCacheAndCancel` 真机测试通过，覆盖实际着色、结果缓存、取消及恢复；原生像素测试通过。
- `warmupLifecycle` 的显式 `smoke` 和 `restart` 模式均通过，覆盖 Worker 复用/重建、后台拒绝与前台恢复、内存压力释放，以及进程重启后无需重新校验。最初一次运行读到了旧的 `restart` 模式文件，在未先建立当前校验记录时断言失败；保留了失败日志，随后补充显式模式参数并按前置条件重测通过。
- AI 子库完整 Node 检查及主应用着色/宿主运行时检查通过。普通应用和测试 HAP 均构建成功，最终应用已覆盖安装到设备，保留用户数据。

原始 JSON、JPEG、阶段日志、构建日志和测试 HAP 保留在本地忽略目录 `output/comic-runtime-20261024/`。其中 `summary.json` 包含逐轮中位数、首次耗时和 JPEG 哈希；`control-*-run.log` 为受控基准记录，`mixed-run.log` 为切换检查。报告日期按开发机日期；设备日志使用设备本地时间，可能显示次日。

重新汇总已保存的数据：

```powershell
node scripts/comic-runtime-report.mjs output/comic-runtime-20261024
```

在已安装相应测试 HAP、已有专用测试图且真实账户满足应用要求的设备上运行单轮：

```powershell
hdc -t <设备地址> shell aa test -b io.legado.read -m entry_test -s unittest ComicRuntimeTestRunner -s runtimeLabel control-optimized -w 300
```

混合序列追加 `-s runtimeMixed true` 并换一个结果标签。结果写入应用缓存 `comic-runtime-<标签>.json`；应检查日志 `TestFinished-ResultCode: 0`，不能只看 hdc 进程退出码。通过 Hypium 运行的功能测试还必须检查 `Failure: 0, Error: 0, Pass: 1`，框架结束码为 0 不代表断言全部通过。

生命周期测试使用 `OpenHarmonyTestRunner`、`-s class 'ComicColor#warmupLifecycle'`。先以 `-s warmupMode smoke` 建立并检查当前环境的校验记录，再以 `-s warmupMode restart` 检查新进程复用；显式参数优先于设备缓存中可能残留的旧模式文件。

本轮未进行跨设备测试、30 分钟持续运行或功耗测量。重复单一素材只能确认当前路径的收益与一致性，后续若要继续提速，应另外测量真实书页分布、宿主排队与首张校验成本。
